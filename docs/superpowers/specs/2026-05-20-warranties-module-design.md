# Warranties Module — Design Spec

**Status:** Approved
**Date:** 2026-05-20

---

## Goal

Implement the `warranties` module to auto-generate warranty records when a work order is completed and expose read/void endpoints. Also add WARRANTY_CLAIM validation to the work orders flow when a new WO references an existing warranty.

---

## Architecture

Repository pattern — one repository, one service, three controllers. `WarrantiesModule` exports `WarrantyService`, which is imported by `WorkOrdersModule`. `WorkOrdersService` calls `WarrantyService` at two points:

1. **On WO completion** → `warrantyService.generateForWorkOrder(workOrderId, organizationId, completedAt)`
2. **On WO creation with `type = WARRANTY_CLAIM`** → `warrantyService.validateClaim(warrantyClaimId, assetId, organizationId)`

No schema migration needed — `Warranty` model already exists.

**Scope:** `Warranty` is scoped to a `WorkOrderItem`, which belongs to a `WorkOrder`, which is branch-scoped. Ownership is resolved through `organizationId` via the work order chain.

## Endpoints

| Method | Path                                   | Description                                   | Roles          |
| ------ | -------------------------------------- | --------------------------------------------- | -------------- |
| `GET`  | `/work-orders/:workOrderId/warranties` | List warranties generated by a WO             | ALL            |
| `GET`  | `/customer-assets/:assetId/warranties` | List all warranties for an asset (across WOs) | ALL            |
| `GET`  | `/warranties/:id`                      | Get a single warranty                         | ALL            |
| `POST` | `/warranties/:id/void`                 | Void a warranty with a reason                 | OWNER, MANAGER |

No pagination on list endpoints — a WO generates at most one warranty per service item; asset history rarely exceeds 20 records.

## Auto-Generation Logic

`warrantyService.generateForWorkOrder(workOrderId, organizationId, completedAt)` is called by `WorkOrdersService` after `inventoryService.commitUsages(id)` when a WO transitions to `COMPLETED`. `completedAt` is the `new Date()` already computed in `updateStatus` — passed directly to avoid an extra DB call.

Steps:

1. Load all `WorkOrderItem` records for the WO, each including the related `Service` (fields: `warrantyDays`, `warrantyDescription`, `warrantyTerm`, `name`)
2. Filter items where `service.warrantyDays` is set and `> 0`
3. For each qualifying item, build a `CreateWarrantyData`:
   - `workOrderItemId` = `item.id`
   - `serviceId` = `item.serviceId`
   - `description` = `service.warrantyDescription ?? service.name`
   - `term` = `service.warrantyTerm ?? null`
   - `validFrom` = `completedAt` of the WO
   - `validUntil` = `completedAt + warrantyDays days`
   - `isVoid` = `false`
4. If no items qualify, return without writing anything — not an error
5. Call `repo.createMany(data)` in a single batch write

`completedAt` is loaded from the WO record before this method is called; `WorkOrdersService` passes `organizationId` so the repository can scope the WO lookup correctly.

## WARRANTY_CLAIM Validation

`warrantyService.validateClaim(warrantyClaimId, assetId, organizationId)` is called by `WorkOrdersService.create()` when `dto.type === WorkOrderType.WARRANTY_CLAIM` and `dto.warrantyClaimId` is present, before persisting the new WO.

Validation order — throws `UnprocessableEntityException` on first failure:

| #   | Check                                                            | Error key                       |
| --- | ---------------------------------------------------------------- | ------------------------------- |
| 1   | Warranty exists in org                                           | `warranty_not_found` (404)      |
| 2   | `isVoid === false`                                               | `warranty_voided` (422)         |
| 3   | `validUntil >= now`                                              | `warranty_expired` (422)        |
| 4   | `warranty → workOrderItem → workOrder → assetId === dto.assetId` | `warranty_asset_mismatch` (422) |

Uses `repo.findForClaimValidation(warrantyClaimId, organizationId)` which returns a `WarrantyWithAsset` type (see Data Shapes).

## Repository Interface

```typescript
interface WarrantyRepositoryInterface {
  createMany(data: CreateWarrantyData[]): Promise<WarrantyRecord[]>
  findById(id: string, organizationId: string): Promise<WarrantyRecord | null>
  findByWorkOrder(
    workOrderId: string,
    organizationId: string
  ): Promise<WarrantyRecord[]>
  findByAsset(
    assetId: string,
    organizationId: string
  ): Promise<WarrantyRecord[]>
  findForClaimValidation(
    warrantyId: string,
    organizationId: string
  ): Promise<WarrantyWithAsset | null>
  void(id: string, reason: string): Promise<WarrantyRecord>
}
```

`findById` and `findByWorkOrder` scope queries via `organizationId` by joining through `workOrderItem → workOrder → branch → organizationId`.

`findByAsset` scopes via `workOrderItem → workOrder → assetId` and `workOrder → branch → organizationId`.

`findForClaimValidation` returns `WarrantyWithAsset` with the `assetId` resolved via join.

## Error Handling

| Condition                                  | Code | Error key                 |
| ------------------------------------------ | ---- | ------------------------- |
| Warranty not found for caller's org        | 404  | `warranty_not_found`      |
| Warranty is voided                         | 422  | `warranty_voided`         |
| Warranty has expired                       | 422  | `warranty_expired`        |
| Asset mismatch on claim                    | 422  | `warranty_asset_mismatch` |
| Warranty already voided (on void endpoint) | 409  | `warranty_already_voided` |

## Activity Log

`POST /warranties/:id/void` records an activity log after a successful void:

```typescript
await activityLogs.record({
  organizationId,
  branchId: warranty.branchId, // from WarrantyRecord — resolved in findById via join
  accountId,
  action: ActivityAction.UPDATED,
  entity: 'Warranty',
  entityId: id,
  metadata: { isVoid: true, reason },
})
```

`WarrantiesModule` imports `ActivityLogsModule`. Auto-generation does not emit a log — it is an internal side effect of the WO completion action which already logs `STATUS_CHANGED`.

## Testing Strategy

`WarrantyService` spec uses `InMemoryWarrantyRepository`. `WorkOrdersService` and `ActivityLogsService` are jest mocks.

**`warranties.service.spec.ts` test cases:**

- `generateForWorkOrder` — creates warranties for all items with `warrantyDays > 0`; skips items with `warrantyDays = null` or `0`; uses `service.name` as fallback when `warrantyDescription` is null; creates nothing and does not throw when no items qualify
- `validateClaim` — passes all checks for a valid warranty; throws 404 `warranty_not_found` when warranty does not exist; throws 422 `warranty_voided` when `isVoid = true`; throws 422 `warranty_expired` when `validUntil < now`; throws 422 `warranty_asset_mismatch` when assets differ
- `findByWorkOrder` — returns warranty list for WO
- `findByAsset` — returns warranty list for asset
- `findOne` — returns warranty; throws 404 when not found
- `void` — voids warranty and returns updated record; throws 409 when already voided; calls `activityLogs.record`

**Controller specs:** RBAC and happy path for each of the three controllers.

**`WorkOrdersService` changes:** Add `WarrantyService` jest mock; add tests for `generateForWorkOrder` being called on COMPLETED transition and `validateClaim` being called on WARRANTY_CLAIM creation.

## Changes to `WorkOrdersModule`

**`work-orders.service.ts`:**

1. Inject `WarrantyService` (no token — plain class injection)
2. In `create()`: if `dto.type === WorkOrderType.WARRANTY_CLAIM && dto.warrantyClaimId`, call `await this.warrantyService.validateClaim(dto.warrantyClaimId, dto.assetId, organizationId)` before `this.workOrders.create(...)`
3. In `updateStatus()`: after `await this.inventoryService.commitUsages(id)`, call `await this.warrantyService.generateForWorkOrder(id, organizationId, completedAt)` — `completedAt` is the `new Date()` already on line 139

**`work-orders.module.ts`:**

- Add `WarrantiesModule` to `imports`
